## 一、当前分销提现机制

### 1.1 完整业务流程

```
用户支付订单
    │
    ▼
① 佣金产生（OrderPayServiceImpl.assignCommission）
    │  ● 检查分销开关（brokerage_func_status）
    │  ● 营销订单（拼团/秒杀/砍价）不参与分佣
    │  ● 向上查找两级推广人
    │  ● 按 SKU 固定金额或系统比例计算佣金
    │  ● 生成 UserBrokerageRecord（状态=创建，金额尚未进入可提现）
    ▼
② 确认收货 → 佣金冻结（StoreOrderTaskServiceImpl.orderReceiving）
    │  ● 佣金记录状态：创建 → 冻结
    │  ● 设置解冻时间 = 当前时间 + 冻结天数
    ▼
③ 定时解冻（BrokerageFrozenTask → UserBrokerageRecordServiceImpl.brokerageThaw）
    │  ● 每小时检查到期的冻结记录
    │  ● 到期记录状态：冻结 → 完成
    │  ● 金额加入用户 brokerage_price（可提现佣金）
    ▼
④ 用户申请提现（UserExtractServiceImpl.extractApply）
    │  ● 校验最低提现额（user_extract_min_price）
    │  ● 从 brokerage_price 扣减
    │  ● 写入 eb_user_extract（status=0 审核中）
    │  ● 写入 UserBrokerageRecord（提现申请记录）
    ▼
⑤ 管理员审核（UserExtractServiceImpl.updateStatus）
    ├─ 通过（status=1）：仅将提现单和佣金流水标记为"完成"
    │                     ⚠️ 不调用任何支付渠道打款 API
    └─ 拒绝（status=-1）：退还 brokerage_price + 记录拒绝流水
    ▼
⑥ 实际打款 → 运营人员线下手动操作
    ● 根据提现记录中的银行卡/微信号/支付宝账号信息
    ● 通过网银或支付平台手动转账
```

**佣金转余额**（独立通道，不经提现表）：
- 入口：`UserRechargeController.transferIn`
- 实现：`UserCenterServiceImpl.transferIn`
- 效果：扣 `brokerage_price`，加 `now_money`

## 二、二清风险分析

### 2.1 什么是"二清"

**二清（二次清算）** 指无支付牌照的机构，先将用户支付的资金归集到自己的账户中，再自行向商户或分销员进行结算的行为。

根据《中国人民银行关于加强支付结算管理防范电信网络新型违法犯罪有关事项的通知》（银发〔2016〕261号）等监管文件，未取得支付业务许可证而从事资金清算的行为属于违规经营支付业务，可能面临：
- 行政处罚（责令停止、罚款）
- 刑事风险（非法经营罪）
- 商户号被封停

### 2.2 当前模式的风险评估

| 维度 | 分析 | 风险等级 |
|------|------|----------|
| **资金归集** | 用户支付的订单款全额进入商户的微信/支付宝商户号，不存在平台统一归集多商户资金 | ⚠️ 中低 |
| **佣金来源** | 佣金是平台在系统内的记账数字（`brokerage_price`），不是从支付通道分账 | ⚠️ 需关注 |
| **提现打款** | 审核通过后由人工线下打款，无自动化支付通道 | ⚠️ 关键风险点 |
| **资金池** | 无独立资金池/托管账户模型，用户佣金以数据库字段形式存在 | ⚠️ 需关注 |
| **微信支付版本** | 使用 API V2（XML + MD5），未接入分账能力 | ⚠️ 缺少合规工具 |

### 2.3 核心风险点

**风险一：典型的"先收后付"模式**

```
用户付款 → 资金 100% 进入商户账户 → 商户手动/自动向分销员打款佣金
```

这个资金流转过程中，商户账户充当了"中间账户"的角色——先归集了包含佣金部分的全部资金，再由商户自行分配。当分销员人数较多、佣金金额较大时，可能被认定为二清行为。

**风险二：未使用支付通道的分账能力**

微信支付和支付宝都提供了「电商收付通」「分账」等合规方案，可以在订单支付时直接按比例分账给接收方，资金不在平台沉淀。当前 CRMEB **未接入**这些分账接口。

**风险三：人工打款的不可控性**

当前的线下人工打款模式，意味着：
- 存在资金滞留在商户账户的时间差
- 无法对打款时效性进行系统级控制
- 缺乏资金流转的可审计链路

## 三、微信合规改造方案

### 3.1 方案选型

| 方案 | 适用场景 | 复杂度 | 推荐度 |
|------|---------|--------|--------|
| **方案A：微信支付分账** | 自营商城 + 分销员返佣 | ⭐⭐⭐ 中等 | ✅ 推荐 |
| **方案B：电商收付通** | 多商户入驻平台 | ⭐⭐⭐⭐⭐ 高 | 多商户才需要 |

**建议采用方案A（微信支付分账）**，因为 CRMEB 是单商户 + 分销员模式，分账 API 足以覆盖。

### 3.2 改造后的架构对比

```
【改造前】
用户付款 → 全额入商户号 → 系统记账佣金 → 人工线下打款给分销员

【改造后】
用户付款（标记 profit_sharing=true）
    → 资金冻结在微信侧
    → 确认收货 + 冻结期结束
    → 微信自动分账给分销员（佣金直达零钱）
    → 剩余资金解冻到商户账户
```

改造后的 `BrokerageFrozenTask` 解冻逻辑：

```java
// 原逻辑：到期 → 直接加 brokerage_price
// 新逻辑：到期 → 检查订单无退款 → 调用微信分账 API → 分账回调成功后再加 brokerage_price
public void brokerageThaw() {
    List<UserBrokerageRecord> thawList = getReadyToThawRecords();
    for (UserBrokerageRecord record : thawList) {
        // 检查关联订单是否有未完成的退款
        if (hasUnfinishedRefund(record.getLinkId())) {
            continue; // 跳过，等退款处理完再分账
        }
        // 调用微信分账 API
        wxProfitSharingService.profitSharing(
            transactionId, orderNo,
            buildReceivers(record)
        );
        // 标记为"分账中"，等回调确认
        record.setStatus(BROKERAGE_RECORD_STATUS_SHARING);
        updateById(record);
    }
}
```

## 四、退款场景处理

### 4.1 延迟分账策略（核心策略，避免大部分退款问题）

**核心思路：不在确认收货时立即分账，而是等过了退款期再分账。**

```
改造前：确认收货 → 立即冻结佣金 → 冻结期后佣金可提现
改造后：确认收货 → 佣金冻结 → 冻结期结束 → 检查无退款 → 调用微信分账 → 佣金直达分销员
```

微信支付允许订单支付后 **180 天内** 完成分账，充足的时间窗口可以覆盖绝大多数退款场景。

利用当前已有的 `extract_time`（佣金冻结时间）配置项来控制延迟分账时间，建议设置为 **7-15 天**。

### 4.2 冻结期内退款（最常见场景）

```
状态：已支付、已确认收货、但还在冻结期内（尚未分账）
概率：高（大多数退款发生在此阶段）
```

**处理流程：**

1. 资金还冻结在微信侧，尚未分出去
2. 调用「解冻剩余资金」API → 资金回到商户账户
3. 调用正常退款流程
4. 将对应的 `UserBrokerageRecord` 状态标记为失效（4）
5. 无需任何额外操作

**代码改造点：** `StoreOrderRefundServiceImpl.refund()`

```java
// 退款前检查分账状态
ProfitSharingRecord sharingRecord = profitSharingRecordService.getByOrderNo(orderNo);
if (sharingRecord != null && sharingRecord.getStatus() == 0) {
    // 尚未分账，先完结分账（解冻资金），再退款
    wxProfitSharingService.finishSharing(transactionId, orderNo);
}
// 然后执行原有退款逻辑
```

### 4.3 分账后退款（少见场景）

```
状态：已分账给分销员、分销员零钱余额充足
概率：低
```

**处理流程：**

1. 调用微信「分账回退」API
2. 微信从分销员零钱中扣回佣金
3. 扣回的金额回到商户账户
4. 执行正常退款流程

### 4.4 分销员零钱不足的兜底方案（极少见场景）

```
状态：已分账、分销员已将零钱花掉/提出
概率：极低（延迟分账策略下几乎不会出现）
```

**分级处理策略：**

#### 第一层：尝试分账回退

```java
try {
    wxProfitSharingService.returnSharing(orderNo, returnOrderNo, receiverUid, amount);
    // 回退成功，正常退款
} catch (InsufficientBalanceException e) {
    // 零钱不足，进入兜底方案
    handleInsufficientBalance(orderNo, receiverUid, amount);
}
```

#### 第二层：部分回退 + 平台垫付

```java
private void handleInsufficientBalance(String orderNo, Integer receiverUid, BigDecimal amount) {
    // 尝试部分回退（能回多少回多少）
    BigDecimal returnedAmount = tryPartialReturn(orderNo, receiverUid, amount);
    BigDecimal remainAmount = amount.subtract(returnedAmount);

    if (remainAmount.compareTo(BigDecimal.ZERO) > 0) {
        // 不足部分：平台先行垫付退款给用户
        // 记录分销员负债
        userService.addDebtBrokerage(receiverUid, remainAmount);

        // 写入负债记录
        UserBrokerageRecord debtRecord = new UserBrokerageRecord();
        debtRecord.setUid(receiverUid);
        debtRecord.setType(BrokerageRecordConstants.BROKERAGE_RECORD_TYPE_SUB);
        debtRecord.setTitle("退款佣金回收（平台垫付）");
        debtRecord.setPrice(remainAmount);
        debtRecord.setMark("订单" + orderNo + "退款，佣金回退不足，平台垫付后待追回");
        userBrokerageRecordService.save(debtRecord);
    }
}
```

#### 第三层：后续佣金自动抵扣负债

在 `brokerageThaw()`（佣金解冻）时增加负债检查：

```java
// 佣金解冻时检查是否有负债
public void brokerageThawWithDebtCheck(UserBrokerageRecord record) {
    User user = userService.getById(record.getUid());
    BigDecimal debtAmount = user.getDebtBrokerage();

    if (debtAmount.compareTo(BigDecimal.ZERO) > 0) {
        // 有负债，新佣金优先抵扣
        BigDecimal thawAmount = record.getPrice();
        if (thawAmount.compareTo(debtAmount) >= 0) {
            // 佣金足够抵扣全部负债
            BigDecimal actualAdd = thawAmount.subtract(debtAmount);
            userService.clearDebtBrokerage(user.getUid());
            userService.operationBrokerage(user.getUid(), actualAdd, user.getBrokeragePrice(), "add");
        } else {
            // 佣金不够，全部用于抵扣负债
            userService.reduceDebtBrokerage(user.getUid(), thawAmount);
            // 本次佣金为 0，不加入可提现
        }
    } else {
        // 无负债，正常解冻
        userService.operationBrokerage(user.getUid(), record.getPrice(), user.getBrokeragePrice(), "add");
    }
}
```

### 综合流程图

```
用户付款（profit_sharing=Y）
  │
  ├─ 微信冻结资金
  │
  ├─ 确认收货 → 佣金进入"待分账"状态
  │
  ├─ 冻结期内退款？
  │   ├─ 是 → 解冻微信资金 + 直接退款 + 佣金失效
  │   └─ 否 → 继续冻结期
  │
  ├─ 冻结期结束 + 无退款申请
  │   └─ 调用微信分账 API → 佣金直达分销员零钱
  │       └─ 解冻剩余资金到商户账户
  │
  └─ 分账后退款？（极少出现）
      ├─ 尝试分账回退
      ├─ 成功 → 正常退款
      └─ 失败（零钱不足）
          ├─ 尝试部分回退
          ├─ 不足部分：平台垫付退款给用户
          ├─ 记录分销员负债
          └─ 后续佣金自动抵扣负债
```

## 五、注意事项与限制

### 微信分账限制

| 限制项 | 说明 |
|--------|------|
| 分账比例 | 默认最高 30%，需向微信申请提高（分销佣金比例较高时注意） |
| 分账时效 | 订单支付后 180 天内必须完成分账，超期资金自动解冻 |
| 接收方上限 | 单个商户号最多添加 2000 个分账接收方 |
| 单次分账接收方 | 单次分账请求最多 50 个接收方 |
| 分账回退时效 | 分账完成后 180 天内可申请回退 |

### 兼容性设计建议

1. **分账功能做开关控制**：新增 `profit_sharing_enabled` 配置项，支持平滑过渡
2. **保留原有人工提现通道**：作为兜底，分账失败时仍可走人工流程
3. **支付宝/银行卡提现不受影响**：分账仅覆盖微信渠道支付的订单
4. **V2 兼容**：分账 API 同时支持 V2 调用，可以不全量升级 V3

### 前置条件

1. 微信商户号需要**开通分账功能**（在微信支付商户平台申请）
2. 如分佣比例 > 30%，需要申请提高分账比例
3. 分销员需绑定微信（确保有 openId）
4. 建议在**微信支付沙箱环境**充分测试后再上线
